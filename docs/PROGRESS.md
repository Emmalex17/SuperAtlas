## Landing-page sticky header fix — 2026-10-24

**User-reported bug:** the landing page's header scrolled away instead of staying pinned at the top while the page scrolled underneath it.

**Root cause:** `.mk-nav` had `position: sticky; top: 0` set correctly — the CSS was never the problem. The header was rendered via `dangerouslySetInnerHTML={{ __html: mkNav() }}` inside an otherwise-empty wrapper `<div>` in each page (`app/page.tsx`, `demo/page.tsx`, `pilot/page.tsx`, `register/page.tsx`). With no other content, that div auto-sized to exactly the header's own height (72px) — and a `position: sticky` element can only float within its own containing block's box. A containing block no taller than the element itself leaves zero room to stick: the moment any scrolling happened, the header immediately exited its box and reverted to normal flow (scrolled away like a static element). Confirmed by moving the header out of the wrapper via a live DOM test (sticky started working immediately, no other change needed), and cross-checked on production in a real, foregrounded Chrome tab (not just the automated preview pane) before concluding this was a genuine bug rather than a test-environment artifact — the automated pane's `window.scrollTo()` calls proved unreliable for this kind of layout check when the pane was backgrounded, which cost significant investigation time before the real-browser cross-check settled it.

**Fix:** converted the header from an HTML string (`mkNav()`) into a real React component, `src/components/landing/SiteHeader.tsx`, rendered directly (no wrapper div) so its containing block is the full-height page container instead. Applied to all four pages that shared the bug. Removed `mkNav()` and the already-dead, already-deprecated `landingPageHtml()` that referenced it; `NAV_LINKS` is now exported from `landingContent.ts` for `SiteHeader` to reuse.

**Verified:** `tsc --noEmit`, `eslint`, `npm run build` all clean. Live-verified on localhost and cross-checked on production: header `rectTop` stays at `0` after scrolling 400-1200px on all four pages (previously tracked scroll distance 1:1, i.e. scrolled fully away); mobile hamburger menu (the `.mk-nav-cb` checkbox-hack) still opens/closes correctly; desktop layout pixel-identical to before. Opened PR #65 (`staging` → `main`), merged (merge commit `b7e694d`), production deployment `success`, confirmed live on `superatlas-green.vercel.app` (`/` and `/demo` both checked directly). `origin/main` = `b7e694d`.

## Sticky sidebar and stray `overline` CSS — found and fixed 2026-10-23

**What the user reported:** the sidebar/topbar scrolled away with the page instead of staying pinned, and a stray line appeared above certain text (KPI card labels, landing page section labels) — described as "underlining" but it was literally CSS `overline` (a line above the text, not below).

**Root causes, both confirmed empirically before fixing (toggled the suspected cause live in the browser and watched the symptom disappear, rather than guessing):**
1. `src/app/layout.tsx` had Tailwind's `min-h-full flex flex-col` utility classes on `<body>`. Making body a column flex container collapsed the `.app` grid container's rendered height to exactly 100vh instead of letting it grow with page content, leaving the sticky sidebar (`.sb{position:sticky;top:0;height:100vh}`) no taller container to stick within — so the whole shell scrolled away with the page. The prototype's `<body>` has no such rule; `globals.css`'s own `html,body{height:100%}` (already present, byte-identical to the prototype) is sufficient on its own. Removed the Tailwind classes from `<body>` and `h-full` from `<html>`.
2. Every `.overline`-styled label (KPI eyebrows, page-head overlines, landing-page section labels) had a literal `text-decoration-line: overline` applied. Cause: Tailwind ships its own built-in `overline` utility class and auto-generates it because the literal class name "overline" appears throughout the markup — colliding with this project's own unrelated `.overline` typography class (small-caps label style) ported verbatim from the prototype. Tailwind's JIT-generated utility sat in a cascade layer that was winning for that one property even though the project's own `.overline{font-size:...}` rule is unlayered and textually later. Fixed by pinning `text-decoration-line: none !important` on the project's `.overline` rule.

**Also found while pushing:** a separate, independently-running session (spawned earlier this session as a background task to fix an unrelated React warning) had pushed its own commit directly to `staging`/`main` in the meantime — `5441bca`/PR #54, restoring app-shell sidebar branding/rail-toggle/mobile-drawer work and an idle-timeout bug fix that had been dropped by an earlier merge. Different files than this fix (`AppShell.tsx` vs `layout.tsx`/`globals.css`), so `git merge origin/staging` resolved with no conflicts. Re-verified both of this fix's issues (sticky sidebar, overline) still hold with that merge in place, and spot-checked the other session's rail-toggle feature still works (it does — an earlier reading of the opposite was a testing-harness artifact: the automated browser pane reports `window.innerWidth: 0` when not actively visible, not a real bug).

Verified against a real production build (`next build && next start`, not just dev mode): sidebar/topbar stay pinned at `top: 0` after scrolling 600px, and no element anywhere on the regulator dashboard, organisation dashboard, or landing page reports a non-`none` text-decoration.
